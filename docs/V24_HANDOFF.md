# 도준이 밥상 v24 — 1차 구현

## 목적
집에 남은 재료와 실제 먹은 반응을 다음 장보기·식단 선택에 연결한다. 기존 단일 index.html 앱과 Firebase 가족 공유 방식을 유지한다.

## 구현
- 장보기에서 월~목 4일 / 금~일 3일 선택. 만들기 목록도 같은 기간으로 계산.
- inventory2: 재료별 수량, g/개/팩, 보관 위치, 메모, 선택적 단위 무게, 수정 시각. 재료별 Firebase 경로에 저장하고 재연결 시 수정 시각으로 병합. 수량 0은 삭제 대신 남겨 다른 기기에서 재등장하지 않게 한다.
- 손질된 재료량 추정치에서 재고를 뺀 부족분 표시. 개/팩의 g 환산은 사용자가 입력했을 때만 사용한다. 조리된 밥과 원물 쌀은 혼동하지 않는다. 계란 등 기존 레시피가 g을 제공하지 않는 재료는 수량 확인 대상으로 표시한다.
- 잘 먹음/보통/조금 먹음/거부, offered_g/eaten_g, 명시적으로 관찰한 재료별 반응과 주식 조리형태 반응 기록. 기존 a/s/l 기록 유지.
- 메뉴 전체 반응과 섭취율은 해당 메뉴 조합에만 적용. 재료와 형태는 직접 기록한 반응만 학습한다. 최근 90일 기록, 30일 반감기, 소수 관측 완화. 재고 보너스는 작게 제한.
- 사용자가 ‘기록 반영해 남은 메뉴 다시 뽑기’를 실행하면 입력 가중치를 월 데이터의 reco에 고정한다. 재고·기록 입력만으로 확정 메뉴를 바꾸지 않는다. 지난 날짜와 기록된 날짜는 fixedPlan으로 보존한다.
- 기존 월령/도입 후보 필터를 유지하고, 간단식 모드의 반찬 단백질에도 도입 여부 필터를 적용한다.
- 준비 알림 파일은 일요일/목요일 반복으로 변경. 앱 내 일정 등록이나 알림 발송은 하지 않는다.

## 검증
`node tests/core.cjs`

Node VM과 저장소·DOM 스텁으로 다음을 확인했다: 90끼 생성과 후보 자격, 220g 필요/180g 재고의 40g 부족, 개/팩 환산, 잘못된 재고 거부, 재료별 병합, 재료/형태 반응 분리, 섭취량 검증과 0g 보존, 기록만으로 식단이 바뀌지 않음, 캐시 유무에 따른 동일 계획 재생성, 기록된 메뉴 보존, 화면 함수 실행.

브라우저 실행 파일을 다운로드할 수 없어 모바일 시각 검증과 실제 클릭 테스트는 아직 완료하지 못했다. 실제 Firebase 두 기기 동기화도 검증하지 않았다. 이 PR은 해당 확인 전까지 초안으로 유지한다. 실제 영양 적합성을 검증한 테스트는 아니다.

## 직접 확인할 순서
1. 테스트용 브라우저에서 기존 데이터 백업 후 v24를 열어 기존 식단·메모가 남는지 확인.
2. 장보기 → 월~목 / 금~일 → 만들기 기간과 부족분 확인.
3. 재고에 소고기 180g 추가, 수량 수정, 전부 사용 저장, 새로고침 후 확인.
4. 150g 제공/0g 또는 85g 섭취 저장, 151g 입력 거부 확인.
5. 전체 메뉴 거부와 단호박 잘 먹음을 따로 기록. 메뉴 다시 뽑기 후 이미 기록된 끼니 유지 확인.
6. 두 기기 모두 같은 버전으로 열어 서로 다른 재료 수정, 같은 재료 수정, 연결 끊김/재연결 후 확인.

## 대화 운영
‘도준이 밥상’ 프로젝트 안에서 식단·섭취 기록 채팅과 앱 개발 채팅을 구분한다. 공통 인수인계는 프로젝트 자료에 두고, 개발 진행 상태와 결정은 GitHub 이슈·PR·이 문서로 확인한다. 별도 프로젝트 사이의 자동 업무 전달은 전제하지 않는다. 대화에서 받은 섭취량이나 재고를 실제 앱에 저장하지 않은 상태에서 저장 완료라고 보고하지 않는다.
